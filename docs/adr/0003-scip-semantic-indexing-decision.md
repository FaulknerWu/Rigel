# ADR-0003: 语义索引主干选型（Tree-sitter + SCIP）

> 返回 [产品需求文档](../prd.md)

## 状态
待定

## 背景
Rigel 当前已经通过 `ADR-0002: 核心语义图谱架构设计` 明确了图数据库只保留身份、关系、摘要和锚点，不存储代码原文；同时在 [实体与关系结构设计规范](../design/entity-relationship-structure.md) 中定义了 `Repository`、`Module`、`File`、`Entity`、`Anchor`、`Summary` 六类核心节点，以及 `CONTAINS`、`DEPENDS_ON`、`SPECIALIZES`、`ALIASES`、`HAS_ANCHOR`、`DESCRIBES` 六类关系族。

这意味着 Rigel 的索引主链路需要同时满足以下约束：

1. **稳定抽取结构骨架**：需可靠构建 `Repository -> Module -> File -> Entity` 及其嵌套层级结构，并为文件和实体生成支持懒加载的精确坐标锚点。
2. **支持跨文件语义解析**：需覆盖定义、引用、实现、类型定义等跨文件关系，避免依赖单一语法树进行脆弱推断。
3. **跨语言统一接入协议**：需制定通用且标准化的语义交互格式，避免为不同语言独立设计中间表示。
4. **源码存储解耦**：语义索引产物应原生支持“图数据库仅存储路径标识与位置坐标，源码本体按需回源”的架构要求。
5. **v1 版本工程可落地性**：优先确保对主流语言、多模块仓库的覆盖以及全量静态索引的可用性，推迟框架级全量语义的实现。

基于这些约束，需要为 Rigel v1 确立“结构层 + 语义层”的正式技术主干。

## 决策
1. **采用混合索引提取主干**：构建由“依赖及描述清单 (Manifest) 扫描”、“Tree-sitter 结构抽取”、“基于编译器前端及 LSP 的 SCIP 语义索引”以及“特定领域提取器 (Domain Extractor) 语义补充”组成的混合架构。
2. **界定 Tree-sitter 结构层职责**：Tree-sitter 专用于提供稳健的语法文件层级提取、结构边界划分、命名实体识别及锚点范围计算。由此主要负责产出 `CONTAINS` 与 `HAS_ANCHOR` 两类主干数据，不承担跨文件语义分析任务。
3. **引入 SCIP 作为统一语义接入层**：采用 SCIP (Semantic Code Intelligence Protocol) 作为项目内通用的数据交换中间格式，但不将 SCIP 视为底层分析器。系统负责消费各语言索引器产出的 SCIP 文档，其底层语义解析依旧交由编译器前端或特定语言的服务支持 (如 `scip-typescript`、`scip-java`、`rust-analyzer`) 完成。
4. **图存储维持与原文本解耦**：系统依赖基于根目录与相对路径 (`project_root` + `relative_path`) 的回源加载机制。SCIP 数据模型内提供的 `Document.text` 仅作后备辅助字段，不作为图数据库的标准储备实体。
5. **拆分框架级与高维业务逻辑**：SCIP 协议不直接处理特定技术栈的高级语义拓扑（如接口路由、ORM 映射表、Proto/GraphQL 定义等）。该部分元数据由独立的特定领域提取器（Domain Extractor）生成，并回写融合至统一图谱模型。
6. **建立显式位置编码坐标系**：系统必须留存显式的文档编码规范。后续 Schema 迭代中需提供包括字节偏移（Byte Offset）及行/列序列（Line/Column）的双轨坐标校验方案，消除或规避由 UTF-8、UTF-16、UTF-32 不同数据偏移机制造成的字符串切片偏差。

## 决策依据

### 选择 Tree-sitter 承载结构提取的缘由
* **高效的增量语法树引擎**：作为增量解析库，Tree-sitter 能够稳定产出具体语法树（Concrete Syntax Tree, CST），极为契合在文件内进行结构边界探测、命名实体分类及层级嵌套解构。
* **规则查询适配能力强**：Tree-sitter 的查询模式匹配（Query Pattern Matching）工具支持直接对类、函数、接口、字段等语法节点执行精确提取，完美对齐确立的节点链路 `File -> Entity`。
* **与 Anchor 模型天然对齐**：各级语法节点原生具备高精度的字符级范围圈定属性，这使其成为生成 `File` 级与 `Entity` 级定位锚点（Anchor）的最佳来源。
* **系统层面界定其能力边界**：Tree-sitter 在结构解析效率极佳，但在跨文件边界推演（如引用溯源、依赖寻址、继承关系解析）中表现不佳。这在逻辑层面确认了架构必须引入专门的语义分析层作为填补。

### 确立 SCIP 作为语义接入标准的基础条件
* **结构化数据表现的同构性**：SCIP 协议框架内部对象结构 (`Document`、`Occurrence`、`SymbolInformation`、`Relationship`) 充分囊括了文件路由、符号定义及其交互模式，可高度兼容 Rigel 目前采用的六大核心关系网模型。
* **原生支持无源码存储设计**：SCIP 协议文档强调将原始凭证 (`Document.text`) 降级为可选提供项，并倡议通过项目根目录以及相对偏置项来进行文件内容寻址。此理念与 Rigel 自身解耦庞大文本占用的初衷一致。
* **跨语言坐标管理的可信度**：在处理跨语系时经常遭遇字符集冲突。而 SCIP 在其内置元数据 (`Metadata.text_document_encoding`) 及文档级别 (`Document.position_encoding`) 中包含了编码方案的确切规定，极大减少了由多类索引器数据交汇时导致的失真问题。
* **社区生态与适配广度达标**：其官方推荐生态已涵盖 Go、TypeScript/JavaScript、C/C++、Java、Scala、Kotlin、Rust、Python、Ruby、C# 等大部分主流现代编程语言组件，完全符合首个验证版本的工程范围预期。
* **对接规范和扩展设计重合**：Sourcegraph 官方在该协议的设计指导中明确指出依赖成熟的编译器前端及 LSP 组件作为前置语义供给服务。这种策略恰好印证了 Rigel 当下收拢规范协议，后撤并托管具体解析器的顶层设计思路。

### 澄清 SCIP 的协议范围与应用局限
* **聚焦于符号标识而非高层业务逻辑**：SCIP 原生建模侧重在文本片段及语法声明的角度输出连接与特征信息，而不会自行解析属于特定框架业务侧的全量衍生映射（如跨语言调用表、ORM Schema 关联、全局环境配置绑定等）。
* **部分核心关系存在二次推算依赖**：一类基础标记（`import`、`read`、`write` 等）能够凭借 `symbol_roles` 直接确立转换规则。但诸如复杂调用 (`calls`) 及重定向引用 (`re-export alias`) 等强关联语义属性通常必须要叠加 Tree-sitter 提供的上下文数据边界（`enclosing_range`）实施多维合并推算。
* **隔离顶层容器环境依赖**：宏观维度的组件集群 (`Module`、`ecosystem`) 及仓库级别信息应当保持对底层语法分析器的隐形。该模块化拓扑应交由工程目录探测器及依赖配置文件（Manifest）负责整合构建。

### 规避或放弃额外技术构想的理由
* **排除“纯 Tree-sitter 独立运行”方案**：由于匮乏跨文件的连通认知能力，若系统依赖完全手写的逻辑去探测复杂文件链接机制，其长期的维护成本和出错率将在多语言支持战略中造成致命隐患。
* **排除“实时联机查询 LSP”方案**：LSP（语言服务器协议）交互模式更匹配编辑器级别的会话生命周期，不匹配代码图谱基座全库处理所需的并发扫盘、幂等落地以及易于多轮测试的纯静态分析流程前提。
* **排除“完全自行研发内部语义提取中间表示（IR）”方案**：自建语义协议并编写分析组件会迫使系统早期阶段将过多资源消耗在适配五花八门的编译器特性上，这违背了首个里程碑版本应当最大效率验证搜索业务可用的战略意图。

## 影响

### 正向收益
* **系统整体职责解构更为明朗**：在执行层面明确划分出 Tree-sitter（结构感知）、SCIP（底层代码语义）、Domain Extractor（领域及框架拓展）三个能力隔离且正交的运行轴面。
* **稳固底层语义图的承接设计**：该技术选型架构足以平滑承载预定计划中的所有节点类及关系边，确保图数据库内维持最佳数据容量及搜索吞吐性能比。
* **标准化后续多语言适配接入步骤**：统一采纳开放的索引准则极大地扫平了未来新语种介入可能带来的障碍及沟通理解成本差异。
* **确保精准可靠的切片源追溯回流**：借由严密的数据锚定映射关系，可以保障后续文本抽离加载任务始终保持正确的逻辑范围。

### 局限与负债
* **与工程构建设施耦合极深**：该套逻辑提取能力深度绑定于代码本身在当前目标编译套件下的正常存活度（如缺乏正确 Gradle 配置时，`scip-java` 组件将引发不可逆错误），需要在解析任务前配备强壮可靠的环境编排探针。
* **索引能力的断层及体验割裂感**：受各开源子项进度制约，多种目标在诸如包引用发现（Cross-repository tracking）等进阶场景中的可用能力参差不齐。此特性落差必定会传递影响最终智能问答响应深度。
* **必须长久供养复杂的抽取拓展库机制**：此项议案未能收缩特定的代码工程框架及特殊配置文件语义层提取工作，为此建立与日常维护各类提取器插件矩阵依旧是系统刚需。
* **数据存储时的坐标系归一化负担**：由于各式分析基底输出代码切分块的参照位（多存在于宽字符编码）各有不同，实施存储链路入库解析时需被强制介入执行一次强制对齐与防偏置偏移转换工序。

## 后续约束与实施指示
1. **重审技术与文档的标准引用对象**：未来产生的各项试验设计和需求文件必须悉数校准并采用“Tree-sitter + SCIP”作为统一词汇定义，废除将 LSIF 视为等价替选品的表述。
2. **扩容定位锚信息机制**：针对即将来临的节点 Schema 设计实操迭代版本，要求在 `Anchor` 定义内显性追加 `byte_offset` 指数支持。在保存文本原始段落信息的定位机制中留任防备解析源错乱的强干预功能。
3. **推演定制中间层的映射词典设计标准**：需专门制定并文档化 `Occurrence.symbol_roles`、SCIP `Relationship` 对象及 AST 闭包区域，如何向高层规范中 `DEPENDS_ON.kind`，`SPECIALIZES` 等字段实施双向翻转及可靠映射的流程准则。
4. **确保特定业务框架识别接口被安全封闭**：对纯语法树工具不适用的、且 SCIP 不能提供的微观及特异级别特征关系，均严格收敛流进专门为其设计的业务拓展端口上。彻底堵死图库乱入混淆或高阶逻辑干涉基础查询层的隐患。
