### Epic 1：索引构建引擎

#### EXP-001: Java AST 与语义解析可行性实验

**优先级：** 必须有

**描述：**
在进入项目基建与数据框架实现前，先完成一次轻量级解析实验，验证 Java AST 骨架抽取与 LSP 语义解析这两段链路是否都可落地，降低后续数据模型设计与索引链路实现的返工风险。

**详细方案：**
[EXP-001 详细实验方案](./exp-001-java-ast-spike.md)

**验收标准：**

- [ ] 选定并验证一套可用的 Java AST 解析方案
- [ ] 使用最小样例仓库或样例源码完成解析实验
- [ ] 验证至少可稳定识别文件、类型、可调用实体三类基础节点，并建立 `defines` 结构骨架
- [ ] 验证可拿到实体名称、限定名、签名、层级归属、源码位置等关键元信息
- [ ] 验证语言服务可解析代表性跨文件符号，并补出 `calls`、`extends`、`implements`、`imports` 等语义边
- [ ] 输出实验结论，明确后续正式实现的解析边界、已知限制、降级策略与风险项

**依赖：** 无

#### FR-002: Java AST 骨架构建与实体抽取

**优先级：** 必须有

**描述：**
系统基于 AST 解析 Java 源码，先构建仓库的结构骨架。该阶段仅依赖单文件语法树与确定性语法信息，负责抽取文件、类型、可调用实体等核心节点，并建立 `defines` 等结构关系。架构上预留多语言解析扩展点，后续可按需接入其他语言。

**验收标准：**

- [ ] 至少支持文件（file）、类型（type）、可调用实体（callable）三类基础节点
- [ ] `type` 至少可区分 `class`、`interface`、`enum`；`callable` 至少可区分 `method`、`constructor`
- [ ] AST 阶段建立 `defines` 关系，用于表达文件到类型、类型到内部类型、类型到方法/构造器的定义归属
- [ ] 每个实体都包含足够定位与区分的元信息，至少包括：名称、限定名、签名、文件路径、包名、起止行号
- [ ] 遇到单文件解析失败时，不阻断整个仓库索引流程
- [ ] 不支持的语法模式记入警告列表

**依赖：** FR-001

---

#### FR-003: LSP 语义关系补全

**优先级：** 必须有

**描述：**
系统在 AST 骨架构建完成后，基于语言服务（LSP）对跨文件符号做定义定位与引用解析，补全实体间的语义关系，用于表达调用依赖、导入依赖、继承扩展与接口实现等联系。该阶段只负责补充需要符号解析才能确认的边，不重复承担 AST 已确定的结构骨架职责。

**验收标准：**

- [ ] 至少支持调用（calls）、导入（imports）、继承（extends）、实现（implements）四种语义关系

**依赖：** FR-002

---

#### FR-004: 增量索引

**优先级：** 必须有

**描述：**
系统支持仅对发生变更的文件执行增量更新，避免每次都全量重建。

**验收标准：**

- [ ] 可检测新增、修改、删除文件
- [ ] 增量索引流程按“AST 骨架重建 -> LSP 语义边补全”两阶段执行，且可分别统计影响范围
- [ ] 增量索引仅重建受影响实体与关系
- [ ] 增量更新的影响范围不限于"变更文件"本身，还必须扩展到：受影响实体、反向关系（引用了变更实体的其他实体）、以及依赖这些实体的摘要与向量
- [ ] 删除文件后，历史实体与关系会被清理
- [ ] 返回本次增量更新影响范围统计

**依赖：** FR-001, FR-003

#### FR-005: 层次化语义摘要与向量表示生成

**优先级：** 必须有

**描述：**
系统通过 LLM 为文件、类型、可调用实体等节点生成可检索的语义表示，作为节点索引。该表示由两部分组成：

1. 源码锚定摘要：可回溯、忠实于源码事实的摘要文本，强制携带源码锚点；
2. 基于实体语义表示生成的 embedding 向量，用于自然语言语义召回。

**验收标准：**

- [ ] 至少为文件、类型、可调用实体三类节点生成语义表示；物理存储方式不做强制约束
- [ ] 每个实体都持久化摘要文本、embedding 向量及生成元信息
- [ ] 摘要必须锚定源码事实，描述职责、输入输出与核心行为，并强制携带源码锚点（文件路径 + 行号范围），支撑后续引用验证
- [ ] 增量索引时仅重算受影响实体的摘要与向量
- [ ] 摘要或向量生成失败时不影响结构索引落库，但必须写入警告与失败原因

**依赖：** FR-002

### Epic 2：检索与证据输出

#### FR-006: 混合召回、子图构建与统一重排

**优先级：** 必须有

**描述：**
系统通过 LLM 将用户的自然语言问题转换为标准的查询语句（具体释义见下文），并通过向量查询从索引中召回相关种子节点，沿关系对种子节点执行多跳扩展，构建与查询语义相关的子图。多个种子节点对应多个子图，需要将重叠部分进行合并。

如何转换：这一步的最终目标是让用户问题更“可检索”。当原问题里有**省略、指代、上下文依赖、模糊表达、决策类问题**时，把它改写成信息完整的查询，通常更利于后续检索器工作。比如用户说“它去年那个政策后来怎么改了”，这里的“它”“那个政策”都不完整；LLM 通过对话的上下文改成“某公司 2025 年隐私政策在后续版本中有哪些修改”，检索目标就更明确，且结果有利于 LLM 分析。

目前所规划的具体方案如下：

- 消除代词和上下文省略
- 把口语问题改成自包含问题

- 补上领域里的同义词、别名、标准术语

- 用 LLM 把复杂问题拆成更聚焦的子查询

- 对原问题做扩展，增加召回面
